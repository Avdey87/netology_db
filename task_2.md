# Задание 1. Резервное копирование
# Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования.
Необходимо описать, какие варианты резервного копирования подходят в случаях:
## 1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.
Для этой задачи оптимально использовать полное резервное копирование (Full Backup), выполняемое ежедневно. В конце каждого рабочего дня создаётся полная копия всей базы данных. При необходимости восстановления достаточно развернуть последний полный бэкап — это даст актуальное состояние базы на момент окончания предыдущего дня.
Альтернативный вариант — дифференциальное резервное копирование (Differential Backup): один полный бэкап делается, например, еженедельно, а ежедневно сохраняются только изменения относительно последнего полного бэкапа. Это экономит место, но восстановление занимает чуть больше времени (полный бэкап + последний дифференциальный).
Плюсы полного бэкапа: простота восстановления, высокая надёжность.
Минусы: требуется больше дискового пространства и времени на создание копии.

## 1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.
Приведите ответ в свободной форме.
Для восстановления на момент, близкий к времени сбоя (с точностью до часа), необходимо использовать инкрементное резервное копирование (Incremental Backup) или транзакционные логи (WAL / Binary Logs).
Схема работы:
Регулярно (например, ежедневно) создаётся полный бэкап.
Между полными бэкапами непрерывно сохраняются журналы изменений — все транзакции, выполненные в базе данных.
При восстановлении сначала разворачивается последний полный бэкап, затем последовательно применяются все инкрементные изменения (или транзакционные логи) вплоть до нужного момента времени (например, за час до сбоя).
Такой подход позволяет восстановить базу данных с точностью до конкретной секунды, что критически важно для финансовых компаний, где потеря даже нескольких минут данных недопустима.

# Задание 2. PostgreSQL
## 2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).
Приведите ответ в свободной форме.

Создание резервной копии (pg_dump)
Базовый синтаксис:
bash
pg_dump dbname > dumpfile
где dbname — имя базы данных, dumpfile — файл для сохранения бэкапа.

Примеры с дополнительными параметрами:
bash
### Создание бэкапа с указанием пользователя и хоста
pg_dump -U postgres -h localhost -d mydb > mydb_backup.sql

### Создание бэкапа с удалённого сервера
pg_dump -h 78.43.11.2 -U postgres -d mydb > mydb_backup.sql[reference:12]

### Создание бэкапа в custom-формате (сжатый, поддерживает pg_restore)
pg_dump -Fc -U postgres -d mydb > mydb_backup.dump[reference:13]

### Создание бэкапа в каталог (directory-формат, позволяет параллельное восстановление)
pg_dump -Fd -U postgres -d mydb -f /backup/mydb_backup[reference:14]
Восстановление базы данных (pg_restore / psql)
Для текстового формата (SQL-скрипт):

bash
psql -U postgres -d mydb < mydb_backup.sql[reference:15]
или

bash
psql -U postgres -f mydb_backup.sql mydb[reference:16]
Для архивных форматов (custom, directory) — используется pg_restore:

bash
### Базовое восстановление
pg_restore -U postgres -d mydb mydb_backup.dump[reference:17]

### Восстановление с удалённого сервера
pg_restore -h db.example.com -p 5432 -U postgres -d mydb mydb_backup.dump[reference:18]

### Восстановление с предварительной очисткой существующих объектов (-c)
pg_restore -U postgres -d mydb -c mydb_backup.dump[reference:19]

### Просмотр содержимого архива перед восстановлением
pg_restore --list mydb_backup.dump > db_list.txt[reference:20]
Ключевые особенности:

pg_dump создаёт логическую (SQL) копию базы данных и может работать при работающем сервере.

pg_restore используется для архивных форматов (-Fc, -Fd) и позволяет выборочно восстанавливать отдельные объекты.

Для резервного копирования глобальных объектов (роли, табличные пространства) используется pg_dumpall.


# Задание 3. MySQL
3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.
Приведите ответ в свободной форме.

В MySQL инкрементное резервное копирование реализуется через бинарные логи (binary logs), в которые записываются все изменения данных.

Базовый принцип
Сначала создаётся полный бэкап (например, с помощью mysqldump или mysqlbackup).

Затем с помощью утилиты mysqlbinlog из бинарных логов извлекаются все изменения, произошедшие после полного бэкапа.

Примеры команд инкрементного бэкапа
1. Создание полного бэкапа с сбросом бинарных логов:

bash
mysqldump -u root -p --all-databases --single-transaction --master-data=2 --flush-logs > full_backup.sql[reference:27]
--flush-logs — создаёт новый бинарный лог-файл, чтобы все последующие изменения записывались в новый файл.

--master-data=2 — записывает в дамп позицию бинарного лога.

2. Создание инкрементного бэкапа (копирование бинарных логов):

bash
# Копирование текущих бинарных логов в отдельную директорию
cp /var/lib/mysql/binlog.* /backup/incremental/[reference:28]

# Или создание SQL-файла с изменениями за определённый период
mysqlbinlog --start-datetime="2025-06-15 00:00:00" --stop-datetime="2025-06-15 23:59:59" /var/lib/mysql/binlog.000001 > incremental_backup.sql[reference:29]
3. Создание инкрементного бэкапа через MySQL Enterprise Backup:

bash
# Полный бэкап (обязателен перед инкрементным)
mysqlbackup --user=root --password=secret --backup-dir=/backup/full backup

# Первый инкрементный бэкап
mysqlbackup --user=root --password=secret --incremental --incremental-base-dir=/backup/full --backup-dir=/backup/inc1 backup[reference:30][reference:31]
Восстановление из инкрементных бэкапов
Для восстановления необходимо последовательно применить:

Полный бэкап.

Все инкрементные бэкапы (бинарные логи) в хронологическом порядке.

bash
### Применение инкрементных изменений из бинарных логов
mysqlbinlog binlog.000001 binlog.000002 binlog.000003 | mysql -u root -p[reference:33][reference:34]

### Применение с указанием временного диапазона
mysqlbinlog --start-datetime="2025-06-15 00:00:00" --stop-datetime="2025-06-15 12:00:00" /var/lib/mysql/binlog.000001 | mysql -u root -p[reference:35]
Ключевые моменты:
Бинарные логи должны быть включены (log_bin = ON в конфигурационном файле).
Инкрементное восстановление позволяет восстановить базу данных на любой момент времени (point-in-time recovery).
Для крупных баз данных рекомендуется использовать специализированные инструменты (MySQL Enterprise Backup, Percona XtraBackup) вместо mysqldump.
